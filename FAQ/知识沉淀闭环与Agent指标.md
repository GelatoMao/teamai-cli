# FAQ：如何识别值得沉淀的知识，并将它变成团队资产？

这份回答围绕“如何发现候选经验、如何评判内容价值、如何提炼和发布、如何通过复用反馈继续维护”展开，将 Agent 术语放到具体决策环节中解释，适用于面对面交流。

实现依据为仓库提交 `f58f315`；示例场景和数字仅用于说明机制。摩擦评分是当前实现，内容价值的判断维度是解释提炼过程的方法，不代表系统已经实现了对应的自动评分器或强制审核关卡。

## 1. 先说整体思路：计算候选会话，再判断具体知识

整体上，我们希望把 AI Coding 过程中产生的有效经验保留下来，让它能够在团队后续的开发中被找到、被理解和被复用，所以这条链路会从 Agent 的执行过程开始，通过 Hooks 采集工具调用、用户干预和执行结果，按 Session 聚合后识别值得回顾的探索过程，再结合会话上下文，判断其中是否形成了有验证依据、适用条件清楚的知识。

## 2. 候选经验从哪里来：用 Hooks 捕捉探索和纠正的证据

候选经验主要来自日常使用 Agent 完成开发任务时产生的探索过程，尤其是用户纠正了 Agent 的判断、某个操作被拒绝，或者工具反复执行失败的会话，因为这些过程里可能包含已有知识没有覆盖的约束、容易踩的坑，以及经过尝试才找到的解决方法，所以我们通过 Hooks 把这些信号记录下来，作为后续复盘的入口。

以 Claude Code 为例，我们在 `UserPromptSubmit` 中记录用户输入摘要并识别纠正候选信号，帮助发现用户在哪里补充了关键约束或调整了方向，在 `PostToolUse` 中记录工具调用，了解这次任务经历了多少探索，再在 `Stop` 时扫描 transcript，补充用户打断、工具拒绝和执行错误等信息，并按 `sessionId` 将这些记录关联起来，用于后续的摩擦评分和候选会话筛选。

这里 Hooks 帮助我们找到的是“值得回顾的过程”，具体要沉淀什么，还需要 Agent 回到会话上下文，梳理用户为什么纠正、原先的尝试为什么失败、最终方案是否经过验证，再把其中有依据、适用条件清楚的结论提炼成 learning，这样才能从一次开发经历中留下别人可以复用的知识。

源码定位：`src/hook-handlers.ts:1151`、`src/dashboard-collector.ts:380`、`src/dashboard-collector.ts:2140`。

## 3. 如何计算：用 friction score 筛选值得复盘的 Session

具体计算时，我们先按 `sessionId` 将 Hook 事件聚合到同一个会话，再分别统计工具调用、用户纠正，以及从 transcript 中识别出的打断、拒绝和执行错误，最后将这些信号组合成 `friction score`，也就是摩擦评分，用来判断这次会话是否值得回顾。

工具调用次数按 `PostToolUse` 对应的 `tool_use` 事件统计，并根据工具名称计算使用了多少种工具；用户纠正 `correction` 则需要结合两个事件判断，也就是 Agent 触发 Stop 后，下一次用户输入是否在六十秒内，并且命中“不对、重来”或 `wrong`、`redo` 等纠正关键词，满足条件就计一次，同一个 Stop 最多匹配一次，避免重复统计；用户打断 `interrupt`、工具拒绝 `toolReject` 和工具执行错误 `toolError` 则通过扫描 transcript 中相应的标记和工具结果识别，其中用户拒绝会从普通工具错误中排除，而且 Stop 扫描得到的是累计数据，多次 Stop 不能直接相加，需要在会话聚合时处理重复快照。

有了这些计数之后，当前实现会给每次用户打断、工具拒绝和用户纠正分别加二十分，对工具错误采用阶梯计分，三到四次加十分、五到七次加十八分、八次及以上加二十五分，再根据是否调用过 Skill 增加五分，根据工具种类多样性最多增加五分，形成基础摩擦评分：

```text
基础摩擦分 =
20 × interrupt
+ 20 × toolReject
+ 20 × correction
+ 工具错误阶梯分
+ Skill 使用加分
+ 工具多样性加分

分享提醒的必要门槛：
最终评分 >= 20，且工具调用次数 >= 15
```

工具错误的阶梯取最高匹配档，不逐档累加；出现 `Skill` 工具调用时加五分，工具多样性最多加五分，具体为 `min(round(不同工具数 / min(工具调用次数, 10) × 5), 5)`。

例如，一个会话发生了一次符合条件的用户纠正、三次工具错误，并且执行了二十次工具调用，那么仅纠正和错误这两项就得到 `20 + 10 = 30` 分，同时满足“最终评分至少二十分、工具调用至少十五次”的提醒门槛，在这个会话还没有提醒过、也没有贡献过知识的情况下，就可以触发分享提醒；如果同样的纠正只发生在三次工具调用的短会话中，自动提醒不会触发，但开发者仍然可以主动发起分享，这个阈值只控制提醒，不限制主动贡献。

另外，系统会考虑知识缺口信号，例如 recall 全部未命中时增加二十分，表示当前已有知识没有为这次任务提供匹配结果；但未命中也可能来自查询表达或覆盖范围问题，因此它仍然只是候选信号，需要在后续内容判断时进一步核实，同一 Session 已经提醒过或者已经贡献过，也会抑制重复提醒。

这里评分衡量的是一次会话中出现了多少值得复盘的信号，分数越高，说明用户干预或探索阻力越明显，而最终能否沉淀，仍然要回到上下文检查是否找到了原因、方案是否经过验证、适用条件是否明确，再决定提炼什么内容。

源码定位：`src/contribute-check.ts:216`、`src/contribute-check.ts:480`、`src/contribute-check.ts:605`、`src/types.ts:2010`。

### 为什么采用这个评分标准？

这套评分的主要考虑，是用较低的计算成本，从大量日常会话中找到值得复盘的过程，同时控制分享提醒的频率，所以采用的是一组可解释的启发式规则，依据是用户干预、工具失败和知识检索缺口等可观测信号；从当前实现可以解释这些规则的作用，但不能将具体权重和阈值说成经过统计训练或实验验证的最优参数。

首先，用户打断、工具拒绝和明确纠正都赋予二十分，是让一次明显的用户干预就能达到分数门槛，因为这些行为可能包含 Agent 尚未掌握的业务约束、操作边界或判断依据，值得进一步回看；不过它们也可能来自用户临时调整需求或操作偏好，因此还需要结合上下文确认具体原因，不能直接据此生成团队规则。

其次，工具错误采用阶梯计分，是考虑到开发过程中偶发失败比较常见，单次错误不足以说明产生了值得沉淀的经验，而反复失败更可能暴露环境配置、工具使用或排查方法上的障碍，所以从三次开始加分，并随着错误次数增加提高分值；阶梯分只取最高匹配档、最高二十五分，也限制了同类错误不断重复时对评分的影响。

工具调用至少十五次的要求，则提供了一个探索工作量门槛，降低短暂交互触发提醒的可能性，而 Skill 使用和工具多样性只提供少量辅助分，反映会话可能涉及可复用的工具或流程组合，这两项合计最多十分，无法独立达到二十分门槛，因此单纯使用了很多工具，也不会仅凭过程复杂就触发分享提醒。

recall 全部未命中时增加二十分，是为了将可能存在的团队知识覆盖缺口纳入候选筛选，如果后续探索形成了经过验证的方法，就可能有补充知识的价值，但未命中也可能来自查询方式，因此仍需在提炼时核实；再配合同一会话只提醒一次、已经贡献后不再提醒的机制，可以进一步控制对正常开发过程的打扰。

对于“为什么恰好是二十分、十五次”这样的追问，更准确的回答是，这些数值构成了当前的启发式初始策略，后续可以通过抽样检查被提醒的会话有多少形成了有效 learning、哪些有价值的会话没有被提醒，以及提醒是否造成打扰，再调整权重和阈值；这是后续校准的方法，不能表述为当前已经验证了最佳参数，也不能将摩擦分直接解释成知识质量分。

## 4. 如何评判：回到上下文，看有没有可复用且有依据的结论

会话被筛选出来之后，share 工作流要求 Agent 回顾问题、关键决策及原因、解决方法、有效工具和踩坑信息，这一步需要从执行记录里找出真正改变结果的决策，并说明它为什么成立；在解释这个判断时，我会重点看问题是否明确、结论是否有依据、适用条件是否清楚，以及下一位使用者能不能照着开展行动，这些是判断内容质量的维度，当前系统并没有把它们全部量化成一个自动通过的知识质量分。

首先要看有没有明确的问题和触发条件，例如“接口调用失败”过于笼统，而“业务层修改没有改变失败现象，进一步检查后发现公共请求配置影响了调用行为”就更容易界定讨论范围；其次要看是否有可追溯的依据，例如相关代码位置、错误输出、修复前后的测试或运行结果，如果目前只提出了一个猜测，就应该保留不确定性，不能写成已经验证的团队结论。

然后要看这条经验能否脱离当时的聊天上下文，被其他成员理解和执行，例如用户说“这里不对”本身没有多少复用价值，但如果能还原为“为什么原来的排查假设不成立、接下来应该检查哪一层、用什么结果判断是否命中原因”，就形成了可迁移的排查方法；同时还要保留边界，避免把一次特定配置问题扩展成“所有接口失败都先改公共层”这样的过度结论。

至于这条内容是否与已有知识重复、是否应补充已有文档，可以结合已有知识检索和维护流程进一步判断，但普通贡献入口没有一个覆盖这些维度的统一强制审核队列，因此面对面介绍时，应该将“内容提炼时采用的判断方法”和“系统已实现的自动检查”明确区分。

## 5. 如何提炼：把一次任务整理成别人能够直接使用的 learning

当我们确认这次排障确实形成了有依据的经验，Agent 就会通过 share 工作流，将原始 transcript 中分散的线索整理为结构化 Markdown，保留任务背景、关键决策及原因、解决方案、有效工具和注意事项，并按照文档模板补充 frontmatter，让内容具备后续检索所需的元数据；提炼的重点是把“当时做了什么”整理成“以后遇到什么情况，可以依据什么信息采取什么行动”。

例如，这次任务最终形成的条目可以围绕“接口异常时如何判断是否需要检查公共请求配置”展开，正文说明当时的失败现象、最初排查业务层为什么没有解决问题、公共配置影响请求的代码依据、最后的修复和验证记录，以及这条经验适用的版本与场景，而不是把二十次工具调用逐条复制进去；如果缺少验证结果或适用范围，就应该明确写出尚未确认的部分。

随后通过 `teamai contribute --file <path> --title "<title>"` 发起贡献，系统先把内容保存到本地 `pending-learnings` 队列并建立检索索引，再尝试提交和推送到团队仓库的 `teamai-learnings` 分支，远端确认送达后才移除对应 pending 内容，如果网络或权限导致失败，就保留本地内容，后续同步时重试。

经过这一步，一条经验获得了稳定的文档载体、检索入口和团队共享路径，普通 learning 发布不创建 PR，因此内容确认需要在分享及团队维护过程中完成，不能将“成功推送”解释为“已经通过人工质量审核”。

源码定位：`skill-data/share/SKILL.md:25`、`skill-data/share/SKILL.md:35`、`src/contribute.ts:47`。

## 6. 最后沉淀成什么：经验知识与代码事实互相补充

在这个闭环里，learning 主要保存问题处理中的判断依据和经验，而代码知识图谱、TeamWiki 则通过代码导入工作流抽取组件、接口、配置及依赖关系，组织成带代码来源的页面与索引，因此对于同一次排障，learning 可以解释“为什么应当检查公共请求配置”，代码知识页面则帮助后续 Agent 找到“公共请求层在哪里、哪些调用方依赖它、相关配置在哪里定义”。

这两类产物有不同来源，当前实现不会把摩擦分达到阈值的 Session 自动变成代码图谱，也不会把一条 learning 自动转换成整套 TeamWiki；比较准确的说法是，会话经验经过提炼进入 learnings，代码事实经过导入进入图谱和 Wiki，再通过共同的检索使用过程为后续任务提供互补上下文。

源码定位：`src/import-codebase.ts:86`、`src/import-codebase.ts:169`。

## 7. 沉淀之后如何继续评判：观察召回和使用证据

recall 承接的是知识进入新任务的过程，当其他成员开始开发时，`SessionStart` 上的后台 pull 先将团队知识同步到本地，用户或 Agent 再根据当前问题发起 `teamai recall "<query>"`，也可以由 `teamai-recall` 子 Agent 先通过 `--check` 做相关性预检，再决定是否完整检索；因此同步、检索和反馈采集是相互配合的环节，Hooks 不会在每次用户输入时自动执行一次完整检索。

实际检索主要在本地完成，其中 learnings、docs、rules、skills 使用 `search-index.json` 中的标题、标签、正文词项和文件路径等信息，代码知识则使用本地 TeamWiki 页面及图谱，索引缺失或过期时可以在本地重建，所以一次 recall 不需要重新访问远端仓库，也不需要重新分析整个代码库。

排序分成两条路径，经验类知识使用关键词匹配和 IDF 加权，标题、标签和正文命中的基础权重分别为三、二、一，再结合领域、条目类型和历史反馈等因素调整，代码知识则使用 BM25 加图谱关系增强，通过命中的节点及一跳、两跳关系补充关联页面，两路结果归一化后合并排序，最终返回最多五条；当前实现没有使用 embedding 向量检索。

结果包含标题、类型、得分、文件路径和内容片段，Agent 需要继续读取正文，核实适用条件和验证依据，代码页面还可能附上来源文件及其新鲜度，通过当前源文件与导入基线的哈希比较，标记为 `current`、`stale`、`missing` 或 `unknown`，帮助 Agent 判断是否需要回到源码确认；这个状态仅说明对应代码来源与基线的关系，不能证明整篇知识仍然完全有效。

为了继续观察知识是否进入任务，一次 recall 会生成唯一的 `run`，记录返回的条目，`PostToolUse` 再通过 `claim` 将检索关联到会话，并在实际读取知识文件时记录 `evidence`，之后由 Stop 等节点上的 `votes-sync` 检查这些信息；默认读取归因要求召回后在二十四小时窗口内成功打开对应文件，并满足会话等关联条件，而召回子 Agent 自己为了检索而读取文件，不直接算作任务侧采纳。

这样就可以区分 `recalled_count` 和 `upvoted_count`，前者表示条目被检索返回的次数，后者可在满足读取归因条件后增加，并按同一会话、同一文档去重，此外也支持显式正向反馈；这些反馈提供的是复用证据，是否真正帮助解决任务，还需要结合实际修改和验证结果判断。

## 8. 如何衡量召回效果，并判断知识是否值得升级？

这里需要先明确“召回率”的口径，当前实现没有单条知识的正式召回率指标，实际记录的是召回次数、正向反馈次数和最后召回时间，并在看板统计知识覆盖率；如果按信息检索中的严格定义，召回率应当是“实际召回的相关知识数 ÷ 所有应当召回的相关知识数”，分母需要相关性标注或评测集，当前这些行为日志本身无法提供这个分母，所以不能直接把某条知识被返回的次数称作召回率。

现有几个指标可以分别回答不同问题，知识覆盖率计算“有过召回记录的条目数 ÷ 条目总数”，表示积累的知识有多少曾被触达，看板按类型统计并取整到百分比；查询命中率可以根据 `hitCount / (hitCount + missCount)` 观察检索是否返回结果，但它不能说明返回内容是否相关，也不直接说明某条 learning 是否值得升级。

对于单条知识，维护流程更关注它是否持续被召回、是否获得正向反馈，以及最近是否仍被使用，因此计算了一个启发式 `confidence`，将使用规模、最近召回时间和正向反馈比例结合起来：

```text
R = recalledCount，即累计召回次数
U = upvotedCount，即累计正向反馈次数
D = 距离最近一次召回的天数

base = min(1, R × 0.1 + U × 0.3)
recency = max(0, 1 - D / 180)
ratio = U / max(1, R)

confidence = round((base × 0.4 + recency × 0.3 + ratio × 0.3) × 100) / 100
```

其中 base 随召回和正向反馈积累而增加，并在一处封顶，recency 在最近召回后随时间逐渐衰减，超过一百八十天降为零，没有最近召回时间时也按零处理，ratio 则提供反馈比例信号；需要注意，召回按返回次数累计，而自动正向反馈按会话和文档去重，正向反馈还可能来自人工操作，因此 `U / R` 只是粗略代理，不能当作真实采用率，当前 ratio 本身也没有封顶，不能保证最终 confidence 始终不超过一。

如果要进一步评估“召回后有多少被读取”，更一致的统计方法是在相同观察窗口内，对同一知识按 Session 去重，用“有符合条件读取证据的会话数 ÷ 召回该知识的会话数”计算召回后的读取比例，并排除人工正向反馈的影响；这是可以进一步构建的评估口径，当前文档不将它表述为系统已有的正式指标，而且即使有读取证据，也不能直接等同于解决了任务。

当前默认的升级候选筛选，要求文档的 confidence 至少为 0.90、累计正向反馈至少五次、至少两位不同用户贡献过正向反馈，并且文档年龄至少十四天、尚未标记 `promoted_to`，其中缺少日期的条目会跳过年龄限制；这些条件共同约束反馈强度、跨成员复用和观察时间，避免单凭召回次数很多就认为知识已经成熟。

例如，假设一条 learning 累计召回十次、正向反馈七次，最近一次召回距今六天，那么 `base = 1`、`recency ≈ 0.967`、`ratio = 0.7`，最终 confidence 为 `0.90`，如果它同时满足至少两位用户反馈、年龄和未升级条件，就可以进入候选；相比之下，召回十次、正向反馈只有一次，即使当天仍被召回，confidence 也只有 `0.73`，更值得先检查内容是否匹配、是否过时，而不是直接升级。

最终进入候选并不会自动改变团队规则，维护者还需要检查内容是否稳定、适用范围是否足够清楚，再通过 `teamai recall promote <learning-id> --category skills|rules|docs` 发起升级，将经验改写为可复用的 Skill、约束性的 Rule 或正式文档，并在原 learning 中记录 `promoted_to`；因此完整判断是先观察召回与使用反馈，再结合 confidence 和跨用户条件筛选，最后确认内容与升级形态。
